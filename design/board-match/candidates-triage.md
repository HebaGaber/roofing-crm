## Deviations (reasons)

1. **Close n tab** (Matches/Close): needs a close-matches query (properties missing exactly one condition); no such API. Tab omitted, header shows Matches n only.
2. **Undo of created leads** (resolved 2026-10-25, no longer a deviation): `leads.undoCreate({ leadKey, leadId? })` returns `{ deleted: true }` or `{ deleted: false, reason }` (`NOT_FOUND`, `NOT_OWNER`, `CHANGED`, `TOO_OLD`, `NOT_UNDOABLE`). The server deletes only when the caller created the lead, it is still New with no later events and it is under 15 minutes old, in one conditional DynamoDB transaction. The list snackbar Undo and the triage Undo send only the leads that action created (with their `leadId`) and show the server's reason in plain words when a lead is kept (`undoCopy.ts`); Skip Undo stays local. The shape differs from the first proposal only by the optional `leadId` guard and the typed `reason`.
3. **Lead marks cover every assignee** (resolved 2026-10-25): marks come from `leads.presence({ requestIdentifiers, fips? })` (BatchGetItem on the lead keys, 100 per call, at most 10 calls per ring), which returns only requestIdentifier, leadKey, leadId and status, so a teammate's lead is marked without exposing its owner or notes. If a ring has more than 1,000 properties, or a presence call fails, the rows still show without those marks and the list and triage say so (`useCandidates` reports `leadsUnavailable` with a reason; status line `CrmCandidatesLeadsUnavailable`: "Lead marks couldn't be checked for this ring, ..." or, over 1,000 properties, "More than 1,000 properties are in this ring, so lead marks are not shown; narrow the radius."); the map's own results rows carry no lead marks, so they have no such note; duplicates are still refused server-side.
4. Triage create origin is "map" (handoff: origin Map); list bulk create uses "list".
5. **Triage entry at 768 px and up** (2026-10-25, tablet pass): the map's panel header shows "Triage n" as a filled button on phones and as an icon button (same accessible name) from 768 px, because the 768 board has no Triage button; the feature stays one tap away. The Candidate list itself has no Triage action.
6. **Lat, lon column** is hidden below 1032 px (see the 768 row); the coordinates stay on the address line.

## Rules kept

Atlas tokens only, no hex; every value from search.properties, search.permits, leads.presence, property.get; missing data shows its reason; bulk create goes through `leads.createMany` (25 per call, one call at a time from the browser; the server runs 3 at once through the same `LeadService.create`); lead marks come from `leads.presence`; no server or e2e files touched.
