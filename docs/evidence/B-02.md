## Known gap: Promote's write, blocked on B-07's table (not a B-02 defect)

`Promote`'s `UpdateCommand` against `crm-leads`'s `META#index` pointer item fails with `ResourceNotFoundException` — the `crm-leads` DynamoDB table does not exist in this environment yet. This is architecturally deliberate, not an oversight: `docs/architecture-constitution.md` §9 and this story's own task list (`tasks.md` T038) both record that **B-07 creates `crm-leads`**; `CrmSync` only ever references it by name for the shared `META#index` pointer item, and never creates a table itself. The critical path for this task (B-01 → B-02 → B-03 → **B-07** → B-09) means `crm-leads` genuinely does not exist until B-07 deploys.

`Validate` already treats a missing table the same as "no run has ever been promoted" (a caught `ResourceNotFoundException`, not a crash), so the reconciliation logic itself runs to completion and reports `"Validated"`, correctly. Only the final atomic pointer flip is blocked. Once B-07 deploys `crm-leads`, re-running this exact same execution input against the already-deployed `CrmSync` stack (no code change needed) will complete `Promote` and flip `META#index.current` — the mechanism (conditional write guarded on the previous value, `#current`/`#previous` DynamoDB reserved-keyword aliases, `SyncDurationMs` emission) is built, unit-tested, and will exercise for the first time at that point.

## Known issue: two vendored scripts retain scraping capability (CLAUDE.md access-boundary)

`packages/oracle-views/scripts/build-gazetteer.ts` (direct HTTP against `census.gov`) and `packages/travis-austin@1.0.0/scripts/socrata.ts` (direct HTTP against Austin's Socrata permits portal) survived the Phase C vendoring pass. CLAUDE.md's access boundary is "read only the Oracle task's published CIDs, `contract/v1` and its MCP. No scraping, no ingestion" — these two scripts are inconsistent with that rule in the same way `a01-us-gis-probe.yml`/`a04-gis-capture.yml` were (those two were removed for exactly this reason during the same vendoring pass; these two were missed).

Neither script is called by any B-02 code path, test, or build step — found by `/code-review medium` and confirmed by grep during the E1 review round (`docs/reviews/CR-B-02.md` finding #5). User decision (Round 1, 2026-10-23): record as a known issue and proceed; do not remove or neutralize the scripts in this story. Revisit if a later story's vendoring pass touches these packages again.

## Defects found and fixed during this live proof

Ten real defects surfaced only once the pipeline ran against real AWS infrastructure (none caught by mocked unit tests, which is itself the point of Phase D's live-runtime requirement, constitution Article XXII) — see `specs/002-lead-index/run-log.md` and the commit history on branch `002-lead-index` for the full detail on each:

1. Lambda handler export-name mismatch (`Runtime.HandlerNotFound`).
2. `PlanResultChoice` crashing on Plan's own success shape (`Condition.stringEquals` on a genuinely absent path).
3. The Map iterating `profiles` (vendored code references) instead of the manifest's actual data-file artifacts.
4. `@duckdb/node-api`'s native binding resolving to the wrong OS/architecture during CDK bundling.
5. The Docker-bundled CDK build image's pnpm failing on registry metadata fetches (`ERR_INVALID_THIS`) — bypassed with a plain npm lockfile for this one native dependency.
6. `FetchPartFunction`'s gateway base-URL environment variables never wired (every part DLQ'd).
7. `PlanPart` missing `cid`/`sha256` (`FetchPart` fetched literally `/ipfs/undefined`).
8. `BuildIndex` crashing on DuckDB's native `Date` objects for timestamp columns.
9. `Validate`'s handler never wired to real inputs (S3 Parquet read, DynamoDB prior-count lookup, `anyPartUnverified` threading) — it only had a tested pure function.
10. `FetchPartsMap`'s result exceeding the 256KB state-size limit once kept (stripped `verifiedBytes` before aggregation); `bucket`/`startedAt` dropped between steps (`LambdaInvoke`'s `outputPath: "$.Payload"` replaces state entirely unless each step echoes what the next one needs); `ValidateResultChoice` crashing on the un-unwrapped `payloadResponseOnly` shape; `Promote`'s DynamoDB expression using the reserved keyword `current` unescaped.
