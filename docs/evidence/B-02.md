## Known gap: Promote's write, blocked on B-07's table (not a B-02 defect)

`Promote`'s `UpdateCommand` against `crm-leads`'s `META#index` pointer item fails with `ResourceNotFoundException` — the `crm-leads` DynamoDB table does not exist in this environment yet. This is architecturally deliberate, not an oversight: `docs/architecture-constitution.md` §9 and this story's own task list (`tasks.md` T038) both record that **B-07 creates `crm-leads`**; `CrmSync` only ever references it by name for the shared `META#index` pointer item, and never creates a table itself. The critical path for this task (B-01 → B-02 → B-03 → **B-07** → B-09) means `crm-leads` genuinely does not exist until B-07 deploys.

`Validate` already treats a missing table the same as "no run has ever been promoted" (a caught `ResourceNotFoundException`, not a crash), so the reconciliation logic itself runs to completion and reports `"Validated"`, correctly. Only the final atomic pointer flip is blocked. Once B-07 deploys `crm-leads`, re-running this exact same execution input against the already-deployed `CrmSync` stack (no code change needed) will complete `Promote` and flip `META#index.current` — the mechanism (conditional write guarded on the previous value, `#current`/`#previous` DynamoDB reserved-keyword aliases, `SyncDurationMs` emission) is built, unit-tested, and will exercise for the first time at that point.

## E2 fixer round (2026-10-23): CR-B-02 findings resolved

Fixed per `docs/reviews/CR-B-02.md`'s scope for E2 (re-scores only `machamp` and `porygon`):

1. **Promote never persisted `propertyCount`/`permitCount`/`promotedAt` onto `META#index`** (critical, confirmed by espeon/alakazam/porygon/code-review). `apps/sync/handlers/promote.ts`'s `UpdateCommand` now also writes `propertyCount`, `permitCount`, `promotedAt` in the same conditional write. `apps/sync/handlers/validate.ts`'s drop-hold check (reads `pointer.Item?.propertyCount`) was always comparing against `undefined`/`null` before this fix and can now actually fire. Extracted the read side into `extractPreviousPromotedPropertyCount()` (exported from `validate.ts`) and proved it reads back exactly what `promoteWithClient` writes in `apps/sync/test/promote.test.ts`. `apps/api/src/adapters/duckDbParquet.ts`'s `indexInfo()` already read the same fields; added a test proving it now returns real values instead of always `0`/`""`.

2. **ADR-02's CloudFront gateway was never wired (machamp's finding)** — decided: **wired it, not a recorded deviation.** `infra/lib/crm-sync-stack.ts`'s own code comment rationalizing the omission claimed CloudFront's `/{cid}` path shape couldn't fit "this shared template" — that turned out to be a one-line fix, not a real blocker: `apps/sync/handlers/fetchPart.ts` now has a `GATEWAY_PART_PATH` map so CloudFront fetches `{base}/{cid}` while Filebase/Pinata keep fetching `{base}/ipfs/{cid}`, and both `PlanFunction` and `FetchPartFunction` now get `GATEWAY_CLOUDFRONT_BASE_URL=https://d2xsqoqv09bd0q.cloudfront.net` (the same host confirmed live in this story's own Stage 0 check, `specs/002-lead-index/run-log.md` A1) ahead of `GATEWAY_FILEBASE_BASE_URL`/`GATEWAY_PINATA_BASE_URL`. `apps/sync/handlers/plan.ts`'s manifest-fetch gateway list was also hard-coded to Filebase/Pinata only; it now reads the same three env vars (falling back to Filebase's/Pinata's public defaults when unset, e.g. local/test runs) via `manifestGatewayUrls()`, trying CloudFront first. No PO decision needed — this was a straightforward implementation gap, not an architectural trade-off requiring sign-off.

3. **Dead, diverging cost gate (code-review/machamp's finding).** `apps/sync/handlers/plan.ts` reimplemented its own inline cost-gate math (`USD_PER_BYTE = 5e-10`, ~6x stricter than `costGate.ts`'s `COST_PER_GB_USD`) and never called `costGate.ts`'s `estimateCostFromManifest`/`evaluateCostGate`, despite a comment claiming it did. `plan.ts` now imports and calls both functions directly; the inline duplicate (`COST_GATE`, `USD_PER_BYTE`, the inline threshold comparison) is deleted. `costGate.ts` is the one place this math lives now.

4. **Unescaped SQL interpolation for `propertyCid` (code-review/espeon's finding).** `apps/api/src/adapters/duckDbParquet.ts` now has one `sqlEscapeString()` helper (DuckDB's single-quote-doubling rule), applied consistently to `propertyUsageType` (already escaped, now via the shared helper) and all three `propertyCid` interpolation sites (`searchPermits`, `getProperty` ×2) that previously were not.

5. *(Out of scope for E2 per the review's own scope note — the two vendored scraping scripts, finding #5 — unchanged; see "Known issue" above.)*

6. **FetchPart's retry loop burned a retry attempt on a throttled wait (confirmed, code-review's finding).** `apps/sync/handlers/fetchPart.ts`'s single `for` loop counter previously incremented on every iteration, including a token-bucket-exhausted `continue` that never called `fetcher.fetch()` — so a run of politeness waits could exhaust `MAX_RETRIES_BEFORE_SWITCH` and switch gateways (or reach the DLQ) without ever having tried the network that many times. Fixed: `attempt` now only increments after a real `fetcher.fetch()` call; bucket waits use a separate, bounded `bucketWaits` counter (capped at 20 per gateway, so a pathological never-refilling bucket still can't hang the handler) and never consume a retry slot. Proven in `apps/sync/test/fetchPart.test.ts`'s new "token-bucket wait never consumes a retry attempt" test: a fake token bucket that refuses twice before admitting, paired with an always-failing fetcher, still drives exactly `MAX_RETRIES_BEFORE_SWITCH` real `fetcher.fetch()` calls (not fewer). The per-Lambda-invocation token-bucket reset remains a real, documented limitation: `createGatewayTokenBuckets()` is still constructed fresh per `FetchPart` invocation, so NFR-002's ≤30 req/min-per-gateway cap is enforced **per invocation, not across the Map's concurrent invocations**. No DynamoDB/ElastiCache-backed shared rate limiter exists in this codebase to reuse, and building one is out of this story's scope — recorded here as a known limitation, not claimed as NFR-002-compliant at the aggregate level. Mitigated in practice by `FETCH_PART_MAP_CONCURRENCY = 3` (bounded Map concurrency) plus the per-invocation bucket still being ≤30/min each, so the realistic aggregate ceiling is ≤90 req/min across a 3-way Map, not unbounded.

7. **Three independent S3-download helpers (code-review's finding).** `apps/sync/handlers/buildIndex.ts`, `apps/sync/handlers/validate.ts` and `apps/api/src/adapters/duckDbParquet.ts` each re-implemented the same `GetObject` → pipe-to-disk helper. Extracted to `packages/observability/src/s3.ts` (`downloadS3ObjectToFile`), exported from the package's index alongside the Powertools middleware — the existing convention for cross-handler/cross-app utilities in this repo. All three call sites now delegate to it.

8. **Orphaned cold-load race (code-review's finding).** `apps/api/src/adapters/duckDbParquet.ts`'s `ensureLoaded`/`coldLoad` raced `load()` against a timeout with no cancellation, so a timed-out load could keep writing to the same on-disk path a later retry also used. Fixed with a per-manifestCid monotonic attempt counter: each cold-load attempt gets its own uniquely-keyed temp directory (never reused across attempts, so no path collision is even possible) and, if an abandoned attempt's `load()` eventually resolves after a newer attempt has already started, it closes its own DuckDB connection and discards itself rather than being returned or cached. Proven in `apps/api/test/duckDbParquet.test.ts`'s new "cold-load race" test using deterministic deferred promises (not real-time delays) to force the exact interleaving: attempt 1 times out mid-download, attempt 2 starts and succeeds, then attempt 1's abandoned download is unblocked and asserted to self-discard (`closeSync` called) without affecting attempt 2's already-cached, still-open connection.
