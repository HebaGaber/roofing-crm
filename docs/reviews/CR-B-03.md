# Code Review: B-03 — Search a radius for aged roofs and open permits, with full detail

Branch `003-map-search`, diffed against `feature/roofing-crm`.

## metagross

**Role note (constitution XVI):** I am both this story's builder and one of its two reviewers, scoring my own work independently per the owner-review article. Scope: are the services/contracts/patterns the ones I'd choose; are my own agent-design.md guardrails actually followed in the delivered code.

### Are the services/contracts/patterns the right ones?

Yes. The shape I proposed in `agent-design.md` — one `search.properties` call returning `{ properties, counts, manifestCid, traceId }`, `search.permits` returning sorted permits with a display-only `isLongOpen` flag, and `property.get` returning a typed null rather than throwing — is exactly what shipped in `apps/api/src/routers/search.ts` and `apps/api/src/routers/property.ts`. Putting the radius/badge/age math in a new `packages/domain` rather than inline in the router or duplicated in the UI was the right call given this is the first story where the map and the API genuinely share a rule (architecture-constitution.md §5); `plan.md`'s Complexity Tracking table correctly justifies introducing it mid-project rather than earlier. The bbox-then-exact-circle two-step in `duckDbParquet.ts` (`bboxFor` as a cheap SQL prefilter, `distanceMeters` as the authoritative cut) is the correct, and only sane, way to do radius search over lat/lng columns in DuckDB without a spatial extension.

### Are my own guardrails followed?

Checked each of the four agent-design.md points against the delivered code:

1. **Query shape / field names verbatim** — followed. `search.ts` returns `properties`/`permits` untouched from the adapter, never renaming `roofAgeYears`/`roofAgeBasis`/`openDays`/`statusClass`.
2. **Permit sort + long-open badge at `openDays > 1826`, never re-derived from `issueDate`** — followed. `packages/domain/src/permit.ts`'s `isLongOpen` is the single implementation; `search.ts`'s `permits` procedure attaches it as a display flag; `PermitChip`/`PropertyDetail` render it, never recompute it. `duckDbParquet.ts`'s permit `ORDER BY` now correctly pins `NULLS LAST` on both sort variants — a fix beyond what I specified, and a good one (DuckDB's default null order is otherwise implementation-defined).
3. **Detail-drawer provenance + BBB-absent state** — followed. `property.ts`'s `bbbFor()` reads `contractorResolution` verbatim and returns `bbb_status: "not_checked"` with a literal reason (`contractor_unresolved` / `no_lexicon_carrier`), matching ADR-08's "always not_checked in v1" and never inventing a rating. `PropertyDetail.tsx`'s `BbbField` renders exactly the required sentence shape, never blank.
4. **No owner name** — confirmed absent from every new router, component, and test.

### What's wrong, risky, or missing

- **Stale/misleading self-disclosure comment (medium).** `apps/api/src/leadIndex.ts`'s top comment states as a "known gap" that `infra/lib/crm-api-stack.ts` does not yet pass `CRM_INDEX_BUCKET_NAME`/`CRM_LEADS_TABLE_NAME` or the S3/DynamoDB grants to the Lambda, and that this "must be closed... before search.* works on the hosted Lambda." That gap is in fact already closed in this same diff: `infra/lib/crm-api-stack.ts` adds `indexBucketName`/`leadsTableName` props, sets both env vars, and grants `indexBucket.grantRead(trpcHandler)` plus `grantReadData` on the leads table; `infra/src/app.ts` wires `dataStack.indexBucket.bucketName` through and adds `apiStack.addDependency(dataStack)`. Leaving the comment unupdated after the infra fix landed could cause a reviewer or the next story's builder to believe the Lambda is still unwired and waste time re-fixing a solved problem, or conversely to distrust an accurate self-disclosure elsewhere in the same file. This is exactly the kind of drift the constitution's honesty rules are meant to catch — low risk since it only affects comments, but it should be corrected before merge.
- **Lambda bundling change is a meaningful, untested-by-CI risk.** `forceDockerBundling: true` plus a side-channel `npm` lockfile (`duckdb-lambda-deps/package-lock.json`) to get `@duckdb/node-api`'s native binding onto `arm64` is a reasonable fix for a real esbuild/pnpm problem (and mirrors `crm-sync-stack.ts`'s precedent), but it is the kind of change that only fails at `cdk deploy` time, not at `cdk synth`/unit test time. `infra/test/stacks.test.ts` was extended (99 lines changed) — worth confirming at Phase Z that this test actually asserts the env vars/grants exist, not just that the stack synths.
- **`search.properties` does two full adapter passes per request.** Computing `counts.afterRadius` and `counts.afterRoofAge` via two separate `searchProperties` calls (one without, one with `roofAgeMinYears`) is correct per FR-004 (both counts must run fresh, uncached, over the full matching set) but doubles DuckDB work on every request with a roof-age filter set. Given NFR-001's p95 < 3 s and the adapter's own 300 ms cold-load budget, this is probably fine at current data volumes, but it's worth watching once the full-county index (A-11) lands — nothing in the diff flags it as a thing to revisit.
- **`property.ts`'s one-BBB-state-per-property simplification is reasonable but under-asserted.** Taking `permits[0]?.contractorResolution` as standing for the whole property's BBB field is explicitly commented as a v1 shortcut ("every permit's contractorResolution agrees in this story's data"), and the test plan's own data snapshot confirms it holds on the current slice. It's a real simplification, not a bug, but there's no test that fails loudly if a future index publishes a property with mixed permit-level `contractorResolution` values — right now it would just silently pick the first permit's state.
- **No new risk introduced in the business-logic layer itself** — `packages/domain`'s three modules are pure, well-tested (65/65 Vitest passing), and match the exact constants/behaviour agent-design.md specified (`LONG_OPEN_THRESHOLD_DAYS = 1826`, `DEFAULT_ROOF_AGE_YEARS = 15`, inclusive boundary).

### Strengths

- The `requireLeadIndex`/`tryLeadIndex` split correctly keeps `health`/`auth` unaffected by the new dependency while giving `search`/`property` a typed `INTERNAL_SERVER_ERROR` instead of a raw `undefined` crash — good defensive design for a Lambda context that's optional until infra wires it.
- Honest edge-case handling throughout: zero-result widen state, outside-county state, `property.get` returning `null` rather than throwing for an unpublished CID, BBB/contractor absence always carrying a stated reason. This matches the constitution's data-honesty article in both the API and the UI layer, not just one.
- Good test discipline: 65/65 Vitest tests pass locally; the SQL `NULLS LAST` fix and the empty-`propertyCids` → `FALSE` short-circuit (avoiding a SQL `IN ()` syntax error) are the sort of defensive details that show real review of the generated SQL, not just happy-path coverage.

### Score: 80/100

Contracts and patterns are exactly the ones I'd choose, the shared-rule layering is correctly applied, and the missing-data/honesty discipline is strong throughout the stack. The deduction is for the stale "known gap" comment in `leadIndex.ts` that no longer matches the infra it ships alongside (a real accuracy problem in a codebase whose central value is honest self-disclosure), plus the unflagged double-query cost and the single-BBB-state-per-property simplification that has no regression test guarding its own assumption.

### What's wrong, risky or missing

1. **The built result cards are never rendered on the Map page (high).** `ResultRow.tsx` (`PropertyFields`, `MissingSummary`, `RowProvenance`) and `PropertyDetail.tsx`/`PermitChip.tsx`/`FilterSheet.tsx` all exist, look correct in isolation, and use Atlas tokens — but `apps/web/src/routes/Map/Map.tsx` (the actual route, lines 95–109) never imports any of them. The results list is a bare `<li>Property {cid}… — roof age {n} yrs ({basis})</li>`, built by hand inline. A repo-wide grep confirms `FilterSheet`, `PropertyDetail`, and `ResultRow` are imported nowhere outside their own files and tests. Practically, the live Map screen looks nothing like `CrmMapPin390.dc.html`/`CrmProperty*.dc.html` — no card chrome, no CID display styling, no provenance line, no permit chip, no contractor/BBB badge, no "Details" button, no roof-age threshold control, no permit-layer toggle. This is the single biggest driver of visual drift, and it means the states this story was supposed to prove (`CrmPropertyPartial390`, `CrmPropertyNoContractor390`) are not reachable by clicking through the shipped UI at all — only by unit-testing the orphaned components directly.
2. **The result card's data shape doesn't match the design's card content (medium, likely a true scope/data gap, not just a rendering miss).** `CrmProperty` (`packages/index-schema`) carries only `latitude`/`longitude`, no `address`, `city`, or precomputed distance/bearing from the pin. The prototype's card spec (CRM-HANDOFF.md "Card:") calls for "address and city · type; distance and bearing from the pin (or 'from you' with GPS)". `ResultRow`'s `PropertyFields` renders raw lat/lon instead, with no distance or bearing field at all. Even once wired up, the card can't match the prototype without either an address lookup or distance/bearing computed from `center`/`radiusMi` (which `packages/domain` already has the haversine for, via `distanceMeters`).
3. **Hardcoded hex colour in `CrmMap.tsx`'s radius ring breaks dark-mode token compliance (low-medium).** `ringGeoJson`'s fill/line paint use literal `"#0B57D0"` for both layers. That value equals the light-mode `--md-sys-color-primary`, but `tokens.css` redefines `--md-sys-color-primary` to `#A8C7FA` under `prefers-color-scheme: dark` — the ring will render the wrong (light-mode) blue in dark mode. MapLibre paint properties can't consume CSS custom properties directly, so this needs `getComputedStyle(document.documentElement).getPropertyValue('--md-sys-color-primary')` read at ring-draw time (and ideally on a `prefers-color-scheme` listener), not a literal string. Flagging as a token-discipline gap rather than an ad hoc colour invented out of nothing, since the value does trace to the token — but as written it will silently drift from the token in dark mode.
4. **`RadiusControl.module.css`'s input corner radius bypasses the shape-token rule (low).** Line 26: `border-radius: var(--space-2)` (8px) on `.input`. The design-system hard rule is "Radii: `--md-sys-shape-corner-*` only" — every other radius in this story's CSS (`CrmMap`, `GpsButton`, `PropertyDetail`, `ResultRow`) correctly uses `--md-sys-shape-corner-*`; this one field slipped through with a spacing token instead. Closest correct token is almost certainly `--md-sys-shape-corner-extra-small` or `-small`; a one-line fix.
5. **GPS state machine omits two named prototype states, with no story AC requiring them — worth a Round-2 confirmation, not a blocker.** The CRM-HANDOFF flow is Explain (`CrmMapGpsExplain390`) → Locating → located/denied/unavailable/outside/low-accuracy. `GpsButton.tsx`'s `GpsState` union has no `explain` state (it calls `getCurrentPosition` immediately on click, state jumps straight to `locating`) and no low-accuracy state (`CrmMapGpsLow390`, the ±500 m threshold). B-03's own "Prototype reference" table only lists `CrmMapGpsDenied390`/`CrmMapGpsOutside390`/`CrmMapLocating390` — not `CrmMapGpsExplain390` or `CrmMapGpsLow390` — so this may be intentionally out of scope for this story and deferred to the E-68 extension; the code comment at the top of `GpsButton.tsx` does flag exact copy as unconfirmed before G7. Still, the explain-before-asking step is part of AC-2's "never a silent failure" spirit and is cheap to add, so it's worth a product-owner call on whether B-03 or a later story owns it.
6. **Minor state-name/board mismatch (cosmetic, affects evidence only).** `GpsButton.tsx`'s `STATE_NAME` map labels the `timeout` case `"CrmMapGpsTimeout390"`, but no such board exists in `design/prototype/` — the prototype folder only has `CrmMapGpsUnavailable390` covering both "unavailable or timed out". Since `STATE_NAME` is only used as a `data-state` attribute for traceability, this won't affect the rendered UI, but it will produce a test/evidence artifact that cites a board that doesn't exist. Should be renamed to `CrmMapGpsUnavailable390` (same as the `unavailable` case) to match the real board, or the two states should be visually distinguished and the prototype updated — whichever the design intends.

### Strengths

- Where components are actually rendered (`CrmMap`'s failed-tile state, `GpsButton`, `RadiusControl`), Atlas tokens are used correctly and consistently for colour, typography, and shape (bar the one radius slip above) — this is not a wholesale token violation, it's isolated.
- 48 px tap targets are correctly implemented everywhere checked: `GpsButton`'s button (`min-height: 48px` literal, matches the `--space-9` convention used elsewhere), `RadiusControl`'s input (`min-height: 48px`), `ResultRow`'s `.details` button and `PropertyDetail`'s `.tab` close button (both `min-width/height: var(--space-9)` = 48px).
- Every GPS failure path (denied, unavailable, timeout, outside-county) renders an explicit, named, on-screen state with `role="alert"`/`role="status"` — never a silent catch or blank map, matching AC-2's letter and the constitution's "a typed state, not an undefined one" principle, even though two extra prototype states aren't modeled (finding 5).
- The missing-data discipline (`MissingReason`, `BbbField`, `RoofAgeGap`, `ContractorBadge`) is honest and specific — no blank fields, no invented values, reasons are rendered verbatim from `missingLabel` — which is the substance the prototype's partial/no-contractor states exist to prove, even though (finding 1) the Map page can't currently reach them through normal use.
- `RadiusControl`'s input-rejection behaviour (out-of-bound value snaps back, no `onChange` fires) is a deliberate, well-reasoned choice over silent clamping and is documented in the code as such.

### Score: 48/100

The individual components are well-built and mostly token-correct, but the story's actual delivered screen does not show them: `Map.tsx` renders a hand-rolled, unstyled list instead of `ResultRow`/`PropertyDetail`/`FilterSheet`/`PermitChip`, so the live Map page has no visual fidelity to `CrmMapPin390`/`CrmProperty*` at all, and the partial/no-contractor states this story names as in scope are unreachable from the UI. That wiring gap, not a token or spacing slip, is the dominant finding and caps the score regardless of the quality of the orphaned components.
