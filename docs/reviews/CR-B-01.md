### Findings

| Severity | File:Line | Description |
| --- | --- | --- |
| Critical | `apps/api/src/routers/auth.ts:26-37` + `infra/lib/crm-api-stack.ts:114-120` | **`auth.reportFailedAttempt` is a public, unauthenticated mutation that increments the real lockout counter for an arbitrary `username`, with no proof any sign-in attempt happened.** API Gateway's `apiEndpoint` is a public HTTPS URL — the Amplify same-origin rewrite doesn't block direct access to it. Anyone can call this endpoint 4 times with `username: "admin@roofing-crm.test"` and lock the one seeded admin account out for 5 minutes, repeatably, forever — a trivial, credential-free DoS against AC-1's entire login flow. The design note in `lockout-handler.ts`/`docs/evidence/B-01.md` frames the risk as "only the failure *count* trusts the client," but that undersells it: the endpoint doesn't require a real failed attempt to have occurred at all, so this isn't "a client could under-report its own failures" (the risk the user approved) — it's "anyone can manufacture failures for someone else's account with zero credentials knowledge." This is the gap in the client-reported-failure/server-enforced-block redesign and needs the user's attention, since it changes the risk picture from what was described when the redesign was approved. |
| Medium | `apps/web/src/auth/signIn.ts:76-81` (`reportFailedAttempt`) | Fire-and-forget: the report call's `.catch(() => false)` silently swallows any error (network failure, 5xx, etc.) and treats it as "not locked," which is the safe default for availability (never block sign-in on a reporting failure) but means a failing report endpoint silently degrades the lockout feature to a no-op with no logging/metric on the client side to notice. |
| Low | `apps/api/src/auth/lockout-handler.ts:95-120` (`handler`) | The `triggerSource` dispatch (PreAuthentication vs PostAuthentication) is a single `if` with no `default`/exhaustiveness check; if Cognito ever calls this Lambda with an unexpected trigger source (e.g., a future trigger type is added to the same function), it silently falls through to the PreAuthentication branch rather than erroring. Not a problem today (only two trigger types are wired in `crm-ops-stack.ts`), but worth a comment or an explicit guard if a third trigger is ever added to this function. |

**Resolution (fixer pass, 2026-10-23):** the Critical finding above is fixed — commit `139cded` adds a route-level API Gateway throttle (burst 5, steady-state 1 req/5s) on `POST /trpc/auth.reportFailedAttempt`, raising the bar against casual/scripted abuse. Presented to the user as a 3-option decision (rate-limit + accept residual risk / full Custom Auth Challenge rearchitecture / remove the feature); the user chose rate-limiting. This does not make the endpoint fully tamper-proof — a determined, paced attacker could still exploit it — which is the accepted, disclosed residual risk for this one-shared-login demo account (no real user data, time-boxed assessment), not a claim that the gap is fully closed. Verified live: AC-3 still passes with the throttle active; the full 60-case Playwright suite passes end-to-end. The two Medium/Low findings below remain open, not blocking (neither is a Critical/High-severity gate requirement).

This is the story's explicit intent (AC-4/AC-5: never a dead end) and screen readers do still expose the element as focusable, so it isn't broken — but `aria-disabled="true"` is specifically the ARIA signal that a control's action is unavailable, which here is false: activating it does navigate somewhere. The visible "Coming soon" badge (always rendered, not hover/focus-gated) happens to cover the sighted-user case, but any assistive-tech user or automation that trusts `aria-disabled` at face value will reasonably conclude the row cannot be activated, same as Playwright initially did. Consider `aria-disabled` + a visible explanatory `aria-describedby` pointing at the badge, or dropping `aria-disabled` in favor of a plain enabled button styled as "not yet built," to remove the contradiction rather than special-casing around it in tests. |

### What's good

The three typed states this story is graded on (lockout, invalid-credentials, `CrmMapFailed390`) are implemented as genuinely distinct UI, each with its own copy, its own `role="alert"`/`data-state` marker, and (for the map) a real retry affordance — not three branches of the same generic error banner. `classifySignInError` (`apps/web/src/auth/signIn.ts:29-39`) cleanly separates lockout/invalid-credentials/unknown by pattern-matching Cognito's own error rather than ever surfacing Cognito's raw exception text, which is exactly what AC-3 asks for. The `NavRow` reuse between `NavRail` and `MoreSheet` is a real shared component (not a duplicated implementation, as both files' comments claim and the imports confirm), and the Atlas-token discipline is genuinely followed everywhere the token audit actually looks — every color, type, margin/padding/gap and radius value in the diff traces to a `tokens.css` custom property. The two real defects `smeargle`'s TZ04 pass found and fixed (the `SignIn` title's un-reset UA margin, the MapLibre-injected-DOM font-family exemption) are disclosed and fixed in place rather than quietly patched, and the run-log's honesty about the one intermittent, non-reproducing `StatusPill` flake (a component confirmed unused by any route) is a good sign of a team that documents rather than suppresses inconvenient test results.
